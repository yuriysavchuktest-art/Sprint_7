# Sprint_7 — API-тесты для Яндекс.Самокат

Проект с автотестами API учебного сервиса **Яндекс.Самокат**:
<https://qa-scooter.education-services.ru/>

Документация: <https://qa-scooter.education-services.ru/docs/>

## Стек

- Java 11+
- Maven
- JUnit 5
- RestAssured
- Allure

## Что проверяется

### Создание курьера (`POST /api/v1/courier`)

- курьера можно создать (201, `ok: true`);
- нельзя создать двух одинаковых курьеров (409);
- нельзя создать курьера с уже существующим логином (409);
- без логина вернётся 400;
- без пароля вернётся 400.

### Авторизация курьера (`POST /api/v1/courier/login`)

- курьер может авторизоваться, в ответе есть `id` (200);
- с неверным паролем вернётся 404;
- под несуществующим пользователем вернётся 404;
- без логина вернётся 400;
- с пустым паролем вернётся 400;
- без пароля — тест отключён (`@Disabled`), см. раздел «Особенности стенда».

### Создание заказа (`POST /api/v1/orders`)

Параметризованный тест проверяет 4 варианта цвета:

- только `BLACK`;
- только `GREY`;
- оба цвета `BLACK` и `GREY`;
- цвет не указан.

В каждом случае проверяются статус 201 и наличие положительного `track` в теле ответа.

### Список заказов (`GET /api/v1/orders`)

- в теле ответа есть непустой массив `orders`;
- запрос с несуществующим `courierId` возвращает 404.

## Логирование запросов и ответов

Во время прогона в консоль автоматически выводятся все запросы и ответы:

- `RequestLoggingFilter` — метод, URL, query-параметры, заголовки и тело запроса;
- `ResponseLoggingFilter` — статус, заголовки и тело ответа;
- JSON печатается с pretty-print;
- те же запросы и ответы прикрепляются к шагам Allure-отчёта через
  `AllureRestAssured`.

Логи видны как при запуске из IDE, так и при запуске через `mvn test`.

## Запуск тестов

В корне проекта:

```bash
mvn clean test
```

При необходимости адрес стенда можно переопределить:

```bash
mvn clean test -Dbase.url=https://another-host
```

## Allure-отчёт

Результаты тестов сохраняются в `target/allure-results`.

Сгенерировать HTML-отчёт:

```bash
mvn allure:report
```

Открыть отчёт:

```bash
mvn allure:serve
```

Готовый отчёт появится в `target/site/allure-maven-plugin/index.html`.

### Добавление отчёта в git

```bash
git add -f .\target\allure-results\.
git commit -m "add allure report"
git push
```

## Независимость тестов и очистка данных

Каждый тест создаёт собственные данные и удаляет их в `@AfterEach`:

- курьеры удаляются через `DELETE /api/v1/courier/{id}`;
- заказы отменяются через `PUT /api/v1/orders/cancel?track={track}`.

Если тест упал до создания данных, очистка просто ничего не делает.
Благодаря этому тесты можно запускать по отдельности и в любом порядке.

## Особенности стенда, обнаруженные при ручном тестировании

1. **Логин без поля `password` зависает.** Запрос `POST /api/v1/courier/login` с одним
   только `login` не возвращает ответ и обрывается по таймауту вместо ожидаемого 400.
   Поэтому соответствующий тест помечен `@Disabled`, а обязательность поля дополнительно
   проверяется тестом с пустым паролем (там сервис корректно отвечает 400).
2. **`firstName` при создании курьера не является обязательным.** Если не передать
   `firstName`, сервис всё равно возвращает 201 и создаёт курьера. Поэтому в тестах
   обязательных полей проверяются реально валидируемые поля — `login` и `password`.
3. **Отмена заказа принимает `track` как query-параметр.** Документация показывает
   `track` в теле запроса, но фактически сервис отвечает 400, если передать его в body.
   Рабочий вариант: `PUT /api/v1/orders/cancel?track=123456`.
